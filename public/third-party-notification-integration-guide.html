H 通知服务接入指南

子应用通过服务端 API 向 H 用户或指定 Email 地址发送受控通知，并查询异步投递状态。

1. 准备 Notification Key

  1. 在 H 的子应用管理中打开目标应用，创建“通知 API Key”。
  2. 创建响应中的明文只显示一次，请立即存入服务端密钥管理系统。
  3. 通过环境变量注入运行环境，不要写入源码、前端包、日志、URL 或版本库。
  4. Key 泄露时立即在 H 中停用或吊销，并签发新 Key 完成轮换。
Notification Key 仅用于通知 API，不是 OIDC Client Secret，也不能在浏览器中调用。本文所有值均为占位符，不含真实密钥。
.env
H_BASE_URL=https://sf.imouto.tech
H_NOTIFICATION_KEY=replace-with-your-notification-key

2. API 概览

项目值或说明
创建通知POST https://sf.imouto.tech/v1/notifications
查询状态GET https://sf.imouto.tech/v1/notifications/:id
认证Authorization: NotificationKey <value>
请求格式Content-Type: application/json

成功响应统一包装为 { "code": 0, "msg": "success", "data": ... }。创建通知时，data 为 { "notificationId": "..." }。创建仅表示 H 已接受并排队处理，不代表 Email 已送达。

3. 收件人

recipients 为数组。推荐使用 H 的 SSO 用户 ID；H 会解析该用户当前绑定的 Email。

SSO 用户与手动 Email
{
  "recipients": [
    { "kind": "user", "userId": 123 },
    { "kind": "email", "email": "recipient@example.com" }
  ]
}
  • kind: "user" 只传正整数 userId，不要同时传 email。
  • kind: "email" 只传合法 email，不要同时传 userId。
  • 手动 Email 收件人必须由管理员在该应用的通知策略中允许，否则返回 403。
  • 解析和去重后每次最多 20 个 Email 收件人；建议调用方自行分批。

4. 使用模板发送

模板由 H 管理员维护。应用只能使用策略授予且已启用的模板；变量名和值都必须符合模板声明。templateKey 以小写字母开头，可使用小写字母、数字以及分段用的 . 或 -；示例 account-alert 是有效值。

cURL · 模板内容
curl --request POST "$H_BASE_URL/v1/notifications" \
  --header "Authorization: NotificationKey $H_NOTIFICATION_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "recipients": [
      { "kind": "user", "userId": 123 }
    ],
    "content": {
      "kind": "template",
      "templateKey": "account-alert",
      "variables": {
        "name": "示例用户",
        "action": "查看详情"
      }
    },
    "idempotencyKey": "account-alert-event-20260813-001"
  }'
模板请求只能包含 templateKey 和 variables，不要同时提交 subject、text 或 html。

5. 直接提交内容

仅当管理员为应用开启“允许直接内容”时可用。subject 和 text 必填，html 可选；H 会按服务端规则清理 HTML。

cURL · 直接内容与手动 Email
curl --request POST "$H_BASE_URL/v1/notifications" \
  --header "Authorization: NotificationKey $H_NOTIFICATION_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "recipients": [
      { "kind": "email", "email": "recipient@example.com" }
    ],
    "content": {
      "kind": "content",
      "subject": "任务处理完成",
      "text": "你的任务已经处理完成，请登录系统查看。",
      "html": "<p>你的任务已经处理完成，请登录系统查看。</p>"
    },
    "idempotencyKey": "task-finished-20260813-001"
  }'
直接内容和手动 Email 是两项独立策略能力。示例同时使用两者，因此应用必须同时获准；无权限时应联系 H 管理员调整策略。

6. TypeScript / JavaScript 示例

notification.ts · Node.js 18+
const baseUrl = process.env.H_BASE_URL ?? 'https://sf.imouto.tech';
const notificationKey = process.env.H_NOTIFICATION_KEY;

if (!notificationKey) throw new Error('H_NOTIFICATION_KEY is required');

async function hRequest(path: string, init: RequestInit = {}) {
  const response = await fetch(`${baseUrl}${path}`, {
    ...init,
    headers: {
      Authorization: `NotificationKey ${notificationKey}`,
      'Content-Type': 'application/json',
      ...init.headers,
    },
  });

  const body = await response.json() as {
    code: number;
    msg: string;
    data: unknown;
  };
  if (!response.ok) {
    throw new Error(`H notification API ${response.status}: ${JSON.stringify(body)}`);
  }
  return body.data;
}

export async function sendAccountAlert(userId: number, eventId: string) {
  return hRequest('/v1/notifications', {
    method: 'POST',
    body: JSON.stringify({
      recipients: [{ kind: 'user', userId }],
      content: {
        kind: 'template',
        templateKey: 'account-alert',
        variables: { name: '示例用户', action: '查看详情' },
      },
      idempotencyKey: `account-alert-${eventId}`,
    }),
  }) as Promise<{ notificationId: string }>;
}

export async function getNotificationStatus(notificationId: string) {
  return hRequest(`/v1/notifications/${encodeURIComponent(notificationId)}`);
}

7. 幂等与状态查询

idempotencyKey 可选，长度为 1–191 个字符。建议使用业务事件类型与不可变事件 ID 组合，并在网络超时重试时复用同一个值。

  • 同一 Key 与相同通知内容重复提交：返回原 notificationId，不会重复创建。
  • 同一 Key 用于不同收件人或内容：返回 409 notification_idempotency_conflict。
  • 不要为每次重试随机生成新 Key，否则无法防止重复通知。
cURL · 查询状态
curl "$H_BASE_URL/v1/notifications/$NOTIFICATION_ID" \
  --header "Authorization: NotificationKey $H_NOTIFICATION_KEY"
状态响应示例
{
  "code": 0,
  "msg": "success",
  "data": {
    "notificationId": "00000000-0000-4000-8000-000000000000",
    "status": "partial_failed",
    "total": 2,
    "sent": 1,
    "failed": 1,
    "pending": 0,
    "errorClasses": { "recipient_rejected": 1 },
    "createdAt": "2026-08-13T08:00:00.000Z",
    "updatedAt": "2026-08-13T08:01:00.000Z"
  }
}

status 可能为 pending、processing、sent、partial_failed 或 failed。仅 sent、partial_failed、failed 是终态。

8. 常见 HTTP 错误

HTTP常见原因与处理
400收件人结构、模板变量或直接内容字段无效；按错误码修正请求，不要原样重试。
401Key 缺失、无效或已停用；检查 Header，并安全轮换 Key。
403应用未获模板、直接内容或手动收件人能力；联系管理员检查应用策略。
404模板不存在，或该 Key 所属应用查不到指定通知；确认 ID 与调用应用。
409模板已停用，或幂等键对应的请求内容发生变化。
429超过速率限制；尊重服务端响应并采用带抖动的指数退避。
503Email 渠道暂不可用；保留相同幂等键后重试，并告警运维人员。

9. 安全与运维建议

  • 所有请求只通过 HTTPS 从可信服务端发出；绝不把 Key 下发给浏览器或移动端。
  • 日志中隐藏 Authorization Header、收件人地址和通知正文，错误日志只保留必要的错误码与请求追踪信息。
  • 为生产、测试环境使用不同 Key；定期轮换并删除不再使用的 Key。
  • 优先使用受控模板，变量只传业务所需的最少数据；不要把密码、Token 或其他秘密写入通知。
  • 超时重试必须复用幂等键；对 429 和可恢复的服务错误限次退避，避免重试风暴。
  • 保存 notificationId 以便追踪异步状态，但不要假设创建成功即代表送达。
